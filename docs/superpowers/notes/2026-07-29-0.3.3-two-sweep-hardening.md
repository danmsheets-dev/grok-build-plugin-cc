# 0.3.3 — two-sweep hardening pass

Date: 2026-07-29
Scope: two independent bug/optimization/feature sweeps (Grok Build audit +
an 8-dimension adversarially-verified ultracode workflow) against the 0.3.2
release, followed by implementation, then a SECOND pair of sweeps against
the resulting diff to catch regressions the fixes themselves introduced.

Suite: 153 tests at 0.3.2 → 214 tests now. Zero known regressions;
everything below was reproduced empirically before and after its fix.

## Round 1 — sweeping 0.3.2

Both sweeps ran independently and largely converged; five findings were
caught by both, which is a strong confidence signal. One finding (`--verify`
silently dropping repeated values) was Grok-only; Ultracode's adversarial
verification stage caught the worktree-teardown data-loss bug that became
the session's most important fix.

### The standout finding: worktree teardown could delete real user data

`removeWorktree` called `git worktree remove --force`, and on Windows git's
own removal code follows a junction it encounters while deleting the tree,
destroying the CONTENTS of whatever real directory it points at. Every
isolated write run links `node_modules`/`.venv`/`target` this way, so this
was not an edge case — it was the normal path. Reproduced directly before
touching any code: an empty `node_modules/` directory survived; a marker
file inside it did not. Fixed by unlinking every reparse point in the
worktree before any removal is attempted, verified against the same
reproduction, and this was the first thing fixed and committed on its own
given the severity.

### Everything else fixed in round 1 (batches, each its own commit)

- **Verify loop correctness** (6 sub-issues): the timeout option was never
  forwarded to `spawnSync` at all (confirmed: a 300ms budget let a 4-second
  command run to completion); only the first failing `--verify` command was
  ever compared to baseline; the fix-and-recheck re-invoke used
  `alwaysApprove: true` unconditionally, escalating a **read-only** run to
  full write access in the user's **real working tree** on its first verify
  failure; usage/cost was overwritten instead of accumulated across
  re-invokes, so `--max-cost` was checked against one call instead of the
  running total; the baseline probe was capped at 120s with its own timeout
  silently discarded, misattributing pre-existing failures on slow
  ecosystems (Godot, cold Rust builds) to the agent; `baselineEntry.ok` was
  captured but never read.
- **Cross-platform**: `cmd.exe /d /s /c` quoting corrupted any verify
  command with an embedded double quote; `splitRawArgumentString` treated
  every backslash as an escape character, deleting every backslash in a
  Windows path; `resolveExecutable` preferred an extensionless POSIX shim
  over a sibling `.cmd` file, which is exactly the shape of
  `node_modules/.bin/*` — reproduced with a synthetic `eslint`/`eslint.cmd`
  pair, and fixing the resolution order surfaced a SECOND bug (Node's
  `spawnSync` cannot invoke a `.cmd` file directly even with the correct
  path), fixed by routing `.cmd`/`.bat` targets through `cmd.exe`.
- **Security**: secrets reached disk and the model unredacted everywhere
  except log lines (job JSON, `--json` output, the verify-fix re-invoke
  prompt); delegate task text was interpolated into a hand-built shell
  string, a real injection path since that text can come from a file, issue,
  or PR the agent read; redaction missed JSON-quoted keys; redaction
  corrupted legitimate diagnostics (`KeyError: 'password'` in a Python
  traceback) — confirmed this reproduced before fixing it, per instruction
  not to invent a fix for an unconfirmed premise.
- **State/process lifecycle**: `SessionEnd` did a read-modify-write outside
  any lock, and a concurrent write from an unrelated session had its job
  file deleted — confirmed directly; a lock file left by a crashed process
  permanently bricked a workspace's state with no recovery path; job-artifact
  pruning's unlinks had no error handling, so a transiently-locked file (a
  Windows AV scanner is the realistic trigger) could abort an unrelated
  run's terminal-status write.
- **Rendering**: `verified`/`worktree`/`budgetStopped` were computed but
  never appended to a delegate run's actual terminal output — the third
  time this exact failure shape has hit this plugin (streaming was inert
  because `outputFormat` was forced to plain; abandoned runs displayed as
  running because the renderer read `job.status` instead of computed
  liveness). The follow-up hint suggested reviewing the working tree for an
  isolated run that never touched it.
- **Ecosystem support**: `PROVISION_LINK_DIRS`/`GENERATED_ARTIFACT_PATTERNS`
  expanded to cover Godot (`.godot`, `.import`), Python (`.tox`,
  `__pypackages__`), and JS/web (`.next`, `.nuxt`, `.svelte-kit`, `.turbo`,
  `.parcel-cache`) — verified end to end for Godot specifically.

## Round 2 — sweeping round 1's own diff

This round's job was explicitly NOT to re-find round 1's issues, but to find
what round 1's fixes themselves introduced. It found two genuine
regressions in code written earlier in this same session, plus three more
real defects in the surrounding land/prune/doctor consistency:

1. **The backslash-escape fix regressed on a common Windows path shape.**
   Stopping ordinary path backslashes from being deleted (round 1) broke a
   *different* case: a quoted path ending in a backslash — exactly what
   Explorer's address bar shows — had its closing quote treated as an
   escaped literal, so the parser swallowed every token after it, including
   a following `--verify` flag. Confirmed directly; fixed by only treating a
   backslash as an escape when the next character is NOT the currently-open
   quote's own closing delimiter.
2. **The stale-lock fix introduced a two-writer race.** A lock file is
   created via `openSync(path, "wx")` and only then has its `{pid,
   createdAt}` payload written by a separate call — an observable window
   where the file exists but is empty. The reclaim logic treated any
   unparseable content as instantly stale with no regard for age, so a
   contender checking during that window reclaimed a brand-new lock after
   ~90ms. Confirmed directly; fixed by falling back to the lock file's own
   mtime rather than assuming missing information means dead, and
   re-verified genuine live contention still correctly waits.
3. **`prune`/`doctor`'s unlanded-work guard checked only the literal string
   `"completed"`**, so a `completed-unverified` or `timed-out` run — with
   real, unlanded commits — fell through to unconditional worktree deletion.
   `doctor` made this worse by recommending `prune --apply` as the fix for
   exactly this case. Confirmed directly: `prune --apply` deleted a real
   agent commit. This is the second data-loss-class finding this session,
   after the worktree junction bug.
4. **`land --preview` used the unchecked `git()` wrapper**, so a stale
   branch ref (most likely an already-landed job) made `git diff` fail with
   empty stdout, silently rendered as "No changes between base and run
   branch" with total confidence. Confirmed directly. Switched to
   `gitChecked`.
5. **`handleLand` never marked a job as landed**, so a second `land` call
   on the same job hit the git-error path above instead of the existing,
   friendlier "no worktree to land" guard. Fixed by clearing the worktree
   field after a successful apply or discard.
6. `land.md` documented the dirty-tree check as expected `--preview` output;
   the code only runs that check on the apply path. Doc corrected.

## Deliberately deferred, with reasons

- **PID-reuse identity verification on the kill path** (`/stop`, SessionEnd
  cleanup). A recycled PID could make the plugin force-kill an unrelated
  process. The correct fix needs cross-platform process-identity
  verification (start time or command name, not just liveness), which is
  exactly the kind of change that deserves its own dedicated round with
  real multi-platform testing, not a fix rushed in alongside everything
  else in this session.
- **Verify command auto-inference** per ecosystem. Real work, but a
  default-on behavioural change I could not validate against real
  Godot/Rust/Python projects in this session — better as its own scoped
  round than shipped undertested.
- **Baseline probes not counted against `--max-duration`** (round 2,
  MEDIUM). A generous 900s-per-command baseline cap can exceed a much
  shorter user-requested overall budget before the agent even starts.
  Consistent with `--max-cost` already being documented as a post-hoc,
  not pre-emptive, budget — noted as a known imprecision rather than fixed.
- **`collectPrunePlan` builds from one state snapshot per invocation**
  (round 2, MEDIUM). Only a real risk under concurrent `prune --apply`
  invocations, an unusual usage pattern; each individual job's
  classification does not depend on any other job's claim in the same run.

## On using Grok Build for the audits themselves

Two very different reliability profiles observed in this session, worth
recording:

- **Write-capable fix delegations (6 of them across both rounds) were
  reliable.** All eventually succeeded with real, empirically-verified
  fixes, correct TDD process, and honest reporting of test counts. One
  first attempt died silently (no heartbeat for 35+ minutes — itself later
  confirmed as an "abandoned" run by the very `doctor`/`prune` machinery
  this session built) and had to be re-run; the retry succeeded.
- **Read-only audit-only delegations were NOT reliable**, failing twice in
  a row for the round-2 second-sweep attempt: once misparsing embedded
  example shell commands in the prompt as if they were bridge flags, once
  returning after only 18 seconds with a one-line "I'll audit..." and
  nothing else — nowhere near enough time to read 8 commits across a dozen
  files. Both failures were silent in the sense that the delegate wrapper
  reported "completed" with no error. This suggests read-only,
  investigation-shaped delegate tasks (as opposed to write-capable,
  fix-shaped ones) may need either `--wait` reinforcement, a smaller scope
  per delegation, or a different prompting pattern than what worked
  reliably for every fix task this session. The ultracode workflow (this
  assistant's own multi-agent orchestration, not the Grok delegate) covered
  the same ground reliably in both rounds and is what actually produced
  the round-2 findings above.
