# Grok Build 0.3.1 and 0.3.2 — safety, then operations

Date: 2026-07-29
Status: approved design, supersedes the 0.4.0/0.5.0 sections of
`2026-07-29-grok-build-safety-and-observability-design.md`

Release numbering: the work previously planned as 0.4.0 ships as **0.3.1**, and
0.5.0 ships as **0.3.2**.

## What changed since the original design

Five amendments come from the field notes written while building 0.3.0 with the
plugin itself (`docs/superpowers/notes/2026-07-29-grok-build-field-notes.md`).
Three more come from reading the Nemotron Build plugin, which already solved
problems this design was about to hit.

### From the field notes

1. **`lastEventAt` is not sufficient.** It only advances when Grok emits an
   event, so a run that dies before its first event still looks alive. 0.3.1 adds
   a worker heartbeat independent of the stream, plus a PID liveness probe.
   Promoted from 0.3.2 to 0.3.1: a tool that reports a dead run as `running` for
   38 minutes undermines every other status it prints.
2. **Record the `grok` CLI version on each run.** The CLI self-updated
   0.2.112 → 0.2.114 within one day of this project. Every behavioural assumption
   we hold is version-dependent, so runs must record which CLI produced them.
3. **The verify loop needs bounds, and the bound is a prompt-shape rule.** The
   40-minute runaway during 0.3.0 happened because a delegation was told to
   "investigate" failures and re-ran the full suite repeatedly. The fix-and-recheck
   prompt must say "fix and re-run only `<cmd>`", never "investigate".
4. **A guard test that no test spawns the real `grok`.** The 0.3.0 money leak was
   silent and would recur on any regressed spawn call.
5. **Session cost aggregation** (moved to 0.3.2, alongside `--max-cost`).

### From the Nemotron Build reference implementation

Nemotron ships worktree isolation and a verify loop already. Three of its
hard-won lessons are adopted directly rather than rediscovered:

6. **`info/exclude` does nothing in a linked worktree.** Git reads excludes from
   the *common* git dir, so a file written to the per-worktree metadata directory
   lands where git never looks. Their unit test passed because it used a plain
   repository rather than a linked worktree — the very case the code existed for.
   Use pathspec magic on the single `git add` instead.
7. **Link heavyweight directories rather than copying.** A fresh worktree has no
   `node_modules`, so the first verify fails with `MODULE_NOT_FOUND`. On Windows a
   **directory junction** works without elevation; on POSIX, a symlink. This
   resolves risk 1 from the original design.
8. **Probe the verify command before the agent runs.** A pre-existing red suite
   must not be blamed on the agent. Capture a baseline failure signature and
   compare against it afterwards.

# 0.3.1 — Isolation, landing, and verification

## Worktree isolation

New `lib/worktree.mjs`, modelled on Nemotron's:

- `resolveWorktreePath(runId, options)` → `${CLAUDE_PLUGIN_DATA}/worktrees/<runId>`,
  deliberately outside the repository so it never appears in `git status`.
- `createWorktree({ cwd, runId, baseRef })` runs
  `git worktree add -b grok-build/<runId> <path> <resolved-rev>`, retrying without
  `-b` when the branch already exists from a crashed run.
- `removeWorktree({ repoRoot, worktreePath, branchName, deleteBranch })` uses
  `git worktree remove --force`, falling back to filesystem removal plus
  `git worktree prune`.
- `commitWorktreeChanges(worktreePath, message)` stages with
  `git add -A -- . :(exclude,glob)**/node_modules/**` and similar pathspecs, so
  build artifacts produced by the verify command never enter the run branch. If
  the pathspec form is rejected by an old git, fall back to plain `add -A` — a
  noisier diff is better than an unstaged fix.
- `artifactExcludePathspecs()` returns those pathspecs. Deliberately excludes
  ambiguous directories: `dist/` and `build/` are committed intentionally by many
  projects and are **not** listed.

`grok` is spawned with `cwd` set to the worktree path. This is proven to control
where it writes; the CLI's native `-w` flag is **silently ignored in headless
`-p` mode** (verified on both 0.2.112 and 0.2.114), so it cannot be used.

Isolation is on by default for `--write` runs. `--no-isolate` opts out. The run
record gains `worktree: { path, branch, baseRef, baseSha }`.

## Dependency provisioning

New `lib/provision.mjs`:

- `planWorktreeLinks(repoRoot, worktreePath, options)` returns link descriptors
  for each of `node_modules`, `.venv`, `venv`, `target`, `vendor` that exists in
  the source repo. Kind is `junction` on Windows, `symlink` elsewhere.
- `provisionWorktree(plan, options)` executes it. **Link failures are recorded,
  never thrown** — provisioning is an optimisation, and a failed link should cost
  a slower verify rather than a failed run.

## The land gate

`/grok-build:land [run-id]`:

- Shows `git diff --stat <baseSha>..<branch>`, then the diff body.
- Asks apply or discard via `AskUserQuestion`.
- Apply squash-merges the run branch onto the live tree, then removes the
  worktree and branch.
- `--discard` removes both without applying.
- Refuses to apply when the live working tree is dirty, naming the conflicting
  files, rather than merging into uncommitted work.

## The verify loop

`--verify "<cmd>"` (repeatable) and `--verify-attempts <n>` (default 2).

Sequence:

1. **Baseline probe.** Before the first model call, run each verify command once
   in the provisioned worktree and record a normalised failure signature. A
   failing probe is data, not an error.
2. Run the agent.
3. Run each verify command again in the worktree.
4. On failure, compare against the baseline signature. Failures present at
   baseline are **not** attributed to the agent.
5. If there are new failures, re-invoke `grok -r <session-id>` with a **bounded**
   prompt: the failing output, and an instruction to fix it and re-run only that
   command. Never "investigate".
6. Repeat to `--verify-attempts`. If new failures remain, the run ends
   `completed-unverified` — never success.

Each verify attempt runs under a timeout derived from the baseline duration:
`baselineMs * 4`, floor 120s, cap 900s.

`completed-unverified` joins `TERMINAL_STATUSES`. Terminal precedence becomes
`cancelled > failed > completed-unverified > completed`, preserving the existing
guarantee that a cancelled run is never overwritten by a finishing worker.

## Liveness: heartbeat, probe, and `abandoned`

- The bridge worker patches `lastHeartbeatAt` every 15 seconds for the whole run,
  independent of stream events.
- `enrichJob` probes tracked PIDs with `process.kill(pid, 0)`. A non-terminal run
  whose `bridgePid` and `agentPid` are both dead is reported as `abandoned`, with
  its last heartbeat age.
- `abandoned` is a display-level classification derived at read time, not a stored
  terminal status. Reaping it into state is `/grok-build:prune` in 0.3.2.

## Run provenance

Each run records `grokVersion`, taken from the existing `getGrokAvailability`
probe, and surfaces it in `show` and `--json`.

## Test hygiene

A guard test asserts that no test ever resolves `grok` to a binary outside the
test's own bin directory. The fixture already logs invocations via
`FAKE_GROK_LOG`; the guard makes the 0.3.0 money leak impossible to reintroduce
silently.

# 0.3.2 — Operations

## Budgets

- `--max-duration <seconds>` — a bridge-side watchdog that calls
  `terminateProcessTree` and records status `timed-out`.
- `--max-turns <n>` — passthrough to the CLI flag, which exists natively.
- `--max-cost <usd>` — evaluated against the `end` event's `total_cost_usd`.
  Because cost is only known when the turn ends, this is a **post-hoc stop**, not
  a pre-emptive cap; the run stops before the *next* turn. Say so in the docs
  rather than implying a hard ceiling.

## Session cost aggregation

`runs --all` gains a footer totalling tokens and dollars across the listed runs,
using the `usage` already stored by 0.3.0. This is the budget-decision feature the
original user feedback asked for.

## `/grok-build:doctor`

Reports, with a suggested fix for each problem: CLI version and auth, `HOME` /
`GROK_HOME` presence, state directory health, orphaned and abandoned runs, stale
worktrees, and installed-plugin-versus-source version drift.

## `/grok-build:prune`

Dry run by default. Reclaims terminal runs past a retention window, worktrees
whose runs have finished, abandoned runs whose PIDs are dead, and orphaned
branches.

## Secret redaction

New `lib/redact.mjs`, applied to log lines and stored stdout before they are
written. Covers the shapes this plugin actually handles: `xai-`, `nvapi-`,
`sk-`, `gh[pousr]_`, bearer tokens, and `KEY=value` pairs whose key name matches
`/(token|secret|key|password)/i`.

## Risks

1. **Isolated-by-default changes a working workflow.** Results no longer appear
   in the working tree until `/land`. The 0.3.1 release notes must lead with this.
2. **Junction creation can fail** on some Windows configurations. Provisioning
   records the failure and continues; the verify command may then fail for
   environmental reasons, which the baseline probe will correctly attribute to the
   environment rather than the agent.
3. **`--max-cost` cannot pre-empt a turn.** Documented as post-hoc.
4. **`grok` CLI drift.** Recording `grokVersion` per run makes drift visible after
   the fact but does not prevent it.

## Testing

Per release, using Node's built-in runner and the fake `grok` fixture:

- 0.3.1 — worktree create/remove/commit against a real temp git repo, including a
  **linked** worktree for the exclude pathspecs (the case Nemotron's test missed);
  junction/symlink planning with a mocked fs; land apply, discard, and
  dirty-tree refusal; verify pass, fail-then-fix, exhausted attempts; baseline
  signature comparison; `completed-unverified` precedence against a concurrent
  stop; heartbeat patching; PID-liveness `abandoned` classification; the
  no-real-grok guard.
- 0.3.2 — duration, turn and cost caps; cost aggregation totals; doctor and prune
  against seeded state; redaction of each supported secret shape.
